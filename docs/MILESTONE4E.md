# Milestone 4E.1: direct-photo transport and native-resolution audit

This is an audit of the pinned UxPlay 1.74 fork at `9f3c2bbc658645533fa1057e76c29ec8c947fa0f` and the owner's LG OLED B7 / Rockhopper 3.9.0 observations. It does **not** enable direct-photo support. The known-good 1080p/30 H.264 mirror and Starfish/ACB paths remain the recovery baseline.

## Confirmed observations and code paths

| Question | Evidence | Conclusion |
| --- | --- | --- |
| Why are Photos items visible at 1080p? | The owner measured 1920×1080 H.264 SPS during playback. This fork's [receiver](../src/receiver.cpp) queues H.264 mirror callbacks, while [the session loop](../src/main.cpp) starts playback from their keyframe. There is no direct-photo presentation callback. | The **observed** playback is consistent with mirroring. The sender's reason for selecting that transport is unknown; no original photo resolution can be inferred from source-library metadata. |
| What did 4D change? | The owner captured bodyless `GET /info HTTP/1.1`, `result=200`, `info_query=none` for a 4K photo, SDR video and 4K HDR video, without further `[direct-probe]` entries. The [development-only gate](../tools/instrument-uxplay.py) returns a binary plist before UxPlay's no-HLS rejection. | The server built an `/info` response. The capture does not prove that the iPhone accepted it. The probe covers only unsupported requests reaching that gate, and is capped/rotated; it cannot rule out RTSP requests, other ports, or a different transport. |
| Which service receives it? | [Receiver startup](../src/receiver.cpp) registers both `_raop._tcp` and `_airplay._tcp` on the same UxPlay HTTP server port. The [pinned dispatcher](https://github.com/FDH2/UxPlay/blob/9f3c2bbc658645533fa1057e76c29ec8c947fa0f/lib/raop.c#L198-L305) distinguishes RTSP/RAOP by `CSeq`, HTTP AirPlay by `X-Apple-Session-ID`, and local HLS by `Host`. | One port does not make the RTSP mirror and AirPlay HTTP media routes interchangeable. The observed bodyless HTTP `/info` has neither `CSeq` nor a session header. |
| Are photo features absent? | Pinned [DNS-SD defaults](https://github.com/FDH2/UxPlay/blob/9f3c2bbc658645533fa1057e76c29ec8c947fa0f/lib/dnssdint.h) are `0x5A7FFEE6` / `0x0`. [Our capability overrides](../src/receiver.cpp) clear bits 0 (video), 4 (HLS) and 42 (multi-codec), and set 27 (legacy pairing). The resulting mask still has bits 1 (photo), 5 (slideshow) and 13 (photo caching) **set**. | Missing photo feature bits are **not** the demonstrated blocker. The existing mask makes legacy photo-related claims this fork cannot fulfill. Changing it may change sender selection and must be tested separately; no bit is changed here. |
| What HTTP routes exist? | The [pinned dispatcher](https://github.com/FDH2/UxPlay/blob/9f3c2bbc658645533fa1057e76c29ec8c947fa0f/lib/raop.c#L377-L455) has RTSP `/info`, HTTP `/server-info`, `/play`, `/reverse`, playback controls and HLS routes, but **no `/photo` or slideshow upload route**. With HLS disabled, ordinary no-`CSeq` HTTP requests are rejected. | A legacy photo upload cannot be accepted by merely setting a DNS-SD bit or enabling HLS. The current `/info` exception does not add photo transfer. |
| Is upstream `/play` a photo route? | The pinned [handler](https://github.com/FDH2/UxPlay/blob/9f3c2bbc658645533fa1057e76c29ec8c947fa0f/lib/http_handlers.h#L665-L875) expects a binary-plist media location and may feed a URL/playlist to a player. [UxPlay's documentation](https://github.com/FDH2/UxPlay/blob/9f3c2bbc658645533fa1057e76c29ec8c947fa0f/README.md) limits supported HLS use to YouTube iOS video. | Enabling `/play` or arbitrary URL fetching would not establish Photos photo support and would introduce unrelated network/player behavior. |
| What might a legacy sender send? | The [open AirPlay protocol notes](https://openairplay.github.io/airplay-spec/photos/http_requests.html#put-photo) document `PUT /photo` with JPEG bytes and a session header. They describe an older protocol, not a capture from this iPhone. | A bounded JPEG `PUT /photo` handler is a plausible *future* experiment, but modern Photos has not been observed to send it to this receiver. HEIC transfer, transformations and 4K source dimensions remain unknown. |

The [4D `/info` writer](https://github.com/FDH2/UxPlay/blob/9f3c2bbc658645533fa1057e76c29ec8c947fa0f/lib/raop_handlers.h#L32-L151) draws its feature mask from DNS-SD and includes receiver identity, public key, model and source version. The feature mask is internally consistent with DNS-SD, **but is not fully truthful about photo handling** because bits 1/5/13 remain set. Its hardcoded keep-alive and status fields have not been validated on Rockhopper. The separate [HTTP `/server-info` handler](https://github.com/FDH2/UxPlay/blob/9f3c2bbc658645533fa1057e76c29ec8c947fa0f/lib/http_handlers.h#L44-L104) hardcodes `0x27F` (including video and HLS) and must not be exposed unchanged as a shortcut.

The pinned dispatcher classifies a new HTTP connection with a session header as AirPlay and can stop an active RAOP mirror while doing so. A session header is an identifier, **not proof of authenticated pairing**; the visible HTTP route selection does not verify a pairing exchange before admitting a new media handler. A future direct-photo route needs a demonstrated authorization boundary, active-sender ownership and a safe transition rule so an unrelated HTTP client cannot upload photos or interrupt mirroring.

## Native 4K still-image feasibility

The B7 panel is 3840×2160, but this application's [SDL shell](../src/shell.cpp) creates a fullscreen window from `SDL_GetCurrentDisplayMode` and uses `SDL_GetRendererOutputSize` for UI layout. It does not record the actual B7 renderer output dimensions, test a 3840×2160 texture, or prove that SDL reaches a native 4K scanout. [LG's app-resolution specification](https://webostv.developer.lge.com/develop/specifications/app-resolution) distinguishes up to **1920×1080 graphics** from **3840×2160 video playback** on UHD sets. That page concerns web apps; it is strong caution, not a measurement of this native SDL application. Therefore native 4K output through SDL is **unverified**, and a 4K decoded image shown in a 1080p renderer must be reported as 1080p presentation/upscaling.

The current [Starfish/ACB backend](../src/media_starfish.cpp) accepts raw H.264 elementary-stream buffers with 720p/1080p bounds. It exposes no still-image feed or verified 4K photo plane in this fork. LG's [webOS 3.5 format table](https://webostv.developer.lge.com/develop/specifications/video-audio-35) lists JPEG/PNG image support and UHD H.264/HEVC **video** support, but does not establish a native-app still-image API or HEIC decoding path. GStreamer is present indirectly through Starfish, not integrated as a photo renderer here. The [private FFmpeg build](../tools/build-deps.sh) enables audio decoders and an H.264 parser only; it disables all other codecs, swscale, filters and format/network components. No JPEG, PNG, HEIC/HEIF, EXIF-orientation or ICC/color-managed decoder is packaged. Display P3-to-output conversion and HDR still-image signaling are likewise absent.

A 3840×2160 RGBA image alone occupies 33,177,600 bytes (about 31.6 MiB). A decoder buffer, SDL texture and encoded payload could require several copies, which matters against the app's 96 MiB `requiredMemory` declaration. Any future decoder must cap compressed bytes, pixel count, allocation count and work time before decoding, and must not block the UI thread.

| Candidate | Status and required evidence |
| --- | --- |
| SDL texture from a bounded JPEG decoder | Plausible for a JPEG-only **1080p** prototype, but no pinned JPEG decoder or TV-renderer-size measurement exists. A 4K texture capability alone would not prove 4K compositor output. |
| Starfish/ACB still-image or 4K video plane | The only validated path is H.264 mirroring at 1080p. A photo-specific feed/output mode and actual scanout size must be demonstrated on Rockhopper before use. Do not substitute a fabricated 4K/HDR status. |
| System image service or GStreamer image pipeline | TV-wide format support does not identify a stable, callable API from this app or its authentication, sandbox, layering and color behavior. Requires a documented or measured firmware-specific contract. |
| HEIC/HEIF or Display P3 | No pinned codec/color-management dependency or sender-format evidence. Keep gated independently from a JPEG/SDR experiment. |

## Decision and next evidence gates

**Stop before a direct-photo prototype or feature-flag change.** The current trace does not identify a photo payload route from modern Photos, the existing HTTP path has no proven pairing/ownership check for a new upload, and the B7's native 4K output route is unmeasured. Implementing `PUT /photo` now would be speculative; additional photo advertisement would deepen the inherited, unfulfilled photo claim.

The next smallest, reversible investigation is a **separate diagnostic build** that (1) records actual SDL display, window and renderer-output dimensions plus texture limits on the B7; and (2) traces fixed-category HTTP/RTSP negotiation outcomes across the relevant dispatcher branches, without raw paths, headers, identifiers or media bytes. It should not enable photo/video features. Repeat ordinary JPEG/HEIC photo, 4K photo, SDR video and 4K HDR video shares with sender iOS version and Photos action recorded externally. If a real JPEG `PUT /photo` follows, first define a pairing/active-sender boundary and bounded JPEG-only route, then independently prove decoded source size and output surface size. Keep the existing 4D package as rollback.

After a verified SDR photo path, prioritize: **(1)** native 4K output mechanism and JPEG/PNG color handling, **(2)** direct 4K SDR video with validated transport and local-only media policy, **(3)** HEVC Main/Main10, **(4)** HDR10/PQ and HLG metadata-to-panel signaling. Dolby Vision is separate. No current CI result can substitute for these B7 measurements.
