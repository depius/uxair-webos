# Milestone 6: experimental HEVC AirPlay mirroring

> Historical development record. See [UxAir 1.2.0 scope](UXAIR_1_2_SCOPE.md) for current release and validation status.

Target: LG OLED B7, Rockhopper 3.9.0, ARMv7 / glibc 2.19. This is a development-app experiment. The owner validated the isolated HEVC probe 0.1.3 with 30/30 3840×2160 Main 8-bit Feed calls accepted, seven FRAMEREADY callbacks, 3840×2160 Starfish video-info and no reported decoder errors. Those observations justify trying the receiver path; they do not prove decoded picture presentation or native UHD output.

## Architecture and limits

The default remains H.264 1280×720/30. In Mirroring, **Video codec → Experimental HEVC / H.265** turns on only DNS-SD feature bit 42 (`SupportsScreenMultiCodec`), while the original direct-video, HLS, HDR and AirPlay 2 claims stay unchanged. Resolution may then be set to 3840×2160/30. The screen advertisement is a maximum/preference; the Apple sender independently chooses the codec and dimensions. The dashboard and `[codec]`/`[session]` logs report what arrived. An H.264 sender remains accepted with HEVC advertisement enabled, within the existing H.264 1080p decoder limit. Changes require disconnecting the sender; the receiver restarts discovery at the new profile without changing its identity or paired keys. Disabling HEVC while 4K is selected restores H.264 720p.

The pinned UxPlay 1.74 mirror transport recognizes `hvc1`, extracts VPS/SPS/PPS from its codec packet, decrypts length-prefixed NAL units and converts them to Annex B. Its original HEVC configuration parsing had unchecked offsets. The checksum-verified development build generates a hardened copy of that exact pinned file: mirror payloads are capped at 2 MiB; `hvc1` VPS/SPS/PPS tags, lengths and NAL headers are bounded before copying; malformed H.264 configuration offsets are also rejected; malformed inputs reset the session. The core version and AirPlay pairing implementation are unchanged. `HevcStream` validates each AU, requires matching VPS/SPS/PPS IDs, accepts only HEVC Main 8-bit 4:2:0 SPS dimensions up to 3840×2160, and waits for a random-access picture before startup/reinitialization. It caches parameter sets across AUs and prepends a valid AUD only if absent. At most 128 NAL units and 2 MiB are accepted per AU.

HEVC uses the existing Starfish/ACB `Media` lifecycle with `codec.video="H265"`, `BUFFERSTREAM`, `RAW`, a 2 MiB source buffer, a 16 MiB receiver queue, remote NTP presentation timestamps and 30 FPS advertised limits. ACB receives logical-screen geometry capped at 1920×1080, as in the successful UHD probe; that is a requested window, not decoded or panel resolution. Feed starts only after LOADCOMPLETED, while `Media::tick` drives Play and ACB state. HEVC startup has an eight-second deadline; Feed backpressure has the existing three-second deadline. Decoder errors, rejected Feed, unsupported dimensions and repeated startup transport resets close the session and restart discovery in H.264 720p for a **new connection**. The app does not assert that the iPhone can switch codecs mid-session. The fallback reason is shown in diagnostics and logged as `[codec] fallback reason=...`. Portrait aspect ratio remains preserved by ACB window fitting, but HEVC input taller than 2160 lines is rejected pending a firmware orientation contract; existing H.264 portrait mirroring is unchanged.

The overlay shows incoming SPS/codec, incoming and accepted-feed FPS, video queue/drops, Starfish video-info, requested ACB window and decoder reinitializations. FRAMEREADY is a sparse firmware callback, not displayed FPS. The 8-bit SPS parser does not establish SDR color transfer from VUI; the app supplies no HDR metadata/output signaling, so the UI calls this *SDR output*. A sender that transmits PQ/HLG metadata is not a supported HDR path. Main10, HDR10, HLG output, 60 FPS, direct Photos/video/HLS and AirPlay 2 direct media remain disabled. In particular, 4K mirroring is not 4K direct-photo transfer.

## Build and validation

`tools/test.sh` runs sanitizer-backed native tests, including pinned `hvc1` length bounds, HEVC Main 8-bit parser, AUD insertion, malformed NALs, reconnection and 1080p→UHD parameter-set changes. The existing H.264, audio, settings, UI, HTTP privacy and diagnostics tests remain in the same suite. GitHub Actions `.github/workflows/ci.yml` runs the Ubuntu suite. `.github/workflows/armv7-ipk.yml` repeats it before building the development IPK on `macos-15` with the checksum-pinned Darwin ARM64 webOS SDK. It runs `tools/verify-elf.py` and `tools/validate-ipk.py` before artifact upload. Download the artifact matching the exact source commit from the development-branch workflow run; verify `SHA256SUMS`, `BUILD_COMMIT.txt` and `ELF_REPORT.txt` in that artifact. A passing build establishes packaging and ABI, not B7 video presentation.

## Manual B7 experiment and rollback

Keep a copy of the previously working development IPK. Install the new `com.github.danlflh.uxplaywebos.dev` IPK manually through webOS Dev Manager. The production app ID is untouched. Existing private data (paired keys, receiver identity, usage history) stays in the development app's state directory; do not uninstall it to upgrade. Launch the app, leave **H.264 only / 720p** selected initially, and confirm pairing plus 720p and 1080p H.264 mirroring and stereo audio. Then disconnect the sender, choose **Experimental HEVC / H.265**, choose **4K / 30 FPS**, reconnect and inspect the detailed diagnostics overlay. Record `[receiver] advertised`, `[codec] negotiated`, `[session] codec/input/advertised`, `[media] Load`, `[smp]` video-info, `[pipeline]`, `[queue-video]` and any `[codec] fallback` lines. Avoid sharing raw pairing or device-identifying log lines.

On the television, compare a known UHD test pattern or source detail with a 1080p control. To claim native UHD, obtain independent output-plane resolution evidence or reliable visual confirmation; a 3840×2160 SPS, accepted Feed and a 3840×2160 video-info event alone are insufficient. Repeat at 1080p HEVC if offered by the sender, then test rapid stop/start, pause/resume, reconnection and H.264 fallback. Do not infer 60 FPS or HDR from a successful 4K SDR session. If the picture is blank or unstable, disconnect the sender, select H.264 only and 720p, then reconnect. If the app cannot be navigated, reinstall the previous development IPK **without uninstalling** to preserve pairing/state. If the media resource stays busy, close the development app and allow the firmware's normal resource cleanup; do not replace libraries or restart media services automatically.

## Hardware-dependent uncertainties

- An iPhone has not yet been observed negotiating HEVC with this receiver. Bit 42 and advertised 4K dimensions are negotiation inputs, not a guarantee of sender behavior.
- The isolated probe used an AUD-delimited local Annex B file without PCM; real AirPlay framing and HEVC+PCM on Rockhopper require actual-device validation.
- Native UHD panel presentation and color transfer remain unmeasured. Starfish video-info is decoder metadata; the ACB window is logical display geometry.
- Firmware callback quiescence after `Unload` is not independently documented. The receiver preserves the existing B7-tested lifecycle and releases each decoder before reinitialization.
