## UxAir playback and limits

- The Starfish development build handles /play independently from RTP screen mirroring. The adapter retains PTTH, event publishing, bounded plist parsing, playback feedback and the existing UxPlay discovery responses. It correlates FCUP responses to the active owner's request ID and URL. With the developer FCUP switch enabled it can request an HTTP(S) manifest through PTTH after a permitted destination returns 403 or 404. Ordinary successful HTTP(S) retrieval makes no FCUP request. Sender-specific non-HTTP URI schemes are outside this experiment.
- The normal launcher selects BUFFERSTREAM. In explicitly selected auto mode, experimental Starfish URI playback gets one attempt through a tokenized loopback relay. A successful segment GET, advancing native playtime and video information or a frame callback establish observable startup. Failed startup can switch once to BUFFERSTREAM after native cleanup succeeds. A failed native unload blocks decoder reuse until app restart. A firmware call that blocks on the application thread remains a separate failure class, with begin/end diagnostics and a hard process deadline in the isolated probe.
- BUFFERSTREAM selects one compatible muxed H.264/AAC variant, reads its VOD TS segments with FFmpeg custom AVIO and feeds Annex B H.264 in decode order with the presentation timestamps expected by the existing Starfish API. AAC-LC ADTS is decoded through the existing audio decoder and resampled to 44.1 kHz stereo PCM on the same timeline. An eight-MiB fetch cap and one prepared segment slot bound work ahead of playback. Seek restarts at the preceding independently decodable segment. Live HLS, fMP4/CMAF, external audio groups, encryption and timestamp discontinuities are outside BUFFERSTREAM's supported scope. The Native URI diagnostic can exercise selected additional formats. Device video, audible playback, sync, transport controls and Safari interoperability require B7 testing.
- Network fetching uses pinned curl/OpenSSL, verified TLS, IPv4 socket address checks and redirect and I/O deadlines. DNS changes are checked again at the socket. FFmpeg has no network protocols enabled and receives only bytes fetched by UxAir. Direct Video discovery defaults on in the Starfish development build. Production and NDL builds omit the Direct Video implementation and discovery.

## November 22 B7 Safari handoff

The Home launcher, pairing, H.264 mirroring and audio-only AirPlay worked on the B7. The Safari in-player AirPlay control left the receiver UI visible. The log shows ALAC audio-only negotiation and generic RTSP POST records. In b72d408 the generic probe runs inside the upstream branch taken when no usable CSeq was recognized. Its path label drops endpoints such as /command. There is no evidence of a queued Direct Video session or a Starfish URI load in the excerpts. The precise request and the reason the sender selected this route are still unknown.

The pinned upstream parser compares header names case-sensitively and reads the protocol adjacent to the URL callback's input span. A valid fragmented request line can therefore reach dispatch with a missing or wrong protocol. These defects also affect Direct requests with differently cased session or content headers. The development parser now uses llhttp's protocol span and parsed version, and recognizes header names regardless of case. The Direct router accepts the known URL controls under HTTP/1.1 and RTSP/1.0 and echoes a validated CSeq when present. It leaves RAOP SETUP, PIN, and transport commands in the existing dispatcher. Explicit URL playback requests still need their own session ID. The reply acknowledges an admitted command and reports loading until decoder progress has been established.

Current UxPlay's source dispatches its URL/HLS endpoint over HTTP and has added direct HTTP(S) URL delivery. Android receiver issue #79 reports a Safari URL handoff that worked after normal HTTPS manifests were separated from FCUP. PhairPlay routes the same URL controls by method and path over either control socket, and treats /command as a separate media-remote channel with binary-plist commands such as updateMRSupportedCommands. RPiPlay implements mirroring. Shairport Sync's AirPlay 2 support describes realtime and buffered audio. Neither provides evidence that those audio or control packets contain a Safari video descriptor. No external code was copied. [UxPlay source](https://github.com/FDH2/UxPlay/blob/48f5ce47c9ef694afccfac907c9e8828329657fe/lib/http_handlers.h) · [Android issue #79](https://github.com/jqssun/android-airplay-server/issues/79) · [PhairPlay routing](https://github.com/JObersi10/PhairPlay/blob/39506518e82e49833f590c7b90007586fa43be9d/app/src/main/kotlin/com/phairplay/airplay/RtspHandler.kt) · [RPiPlay](https://github.com/FD-/RPiPlay) · [Shairport Sync](https://github.com/mikebrady/shairport-sync/blob/master/AIRPLAY2.md)

Discovery keeps the existing AppleTV3,2 model, 220.68 source version, and bits 0 and 4 for experimental video/HLS. The combined TXT query, binary qualifier, and plain discovery replies use the same live service records and feature mask as Bonjour. No additional capabilities are advertised. The application has no general AirPlay 2 media-queue transport, buffered-audio engine or protected video transport. An unsupported negotiated transport would require evidence of its setup and descriptors before implementing it.

The generated dispatcher now records route, protocol, exact known endpoint, response status, and allowlisted media-control or numeric stream categories before the request is destroyed. Unrecognized paths are redacted, as are all query values and wire identifiers. A separate admission line gives the media descriptor kind and whether a session was queued. A subsequent backend line identifies the strategy. If the B7 again shows only media-control or audio setup, that trace determines which protocol is missing. If it shows an admitted URL session, the same trace follows Native URI attempts, BUFFERSTREAM fallback and decoder progress.

BUFFERSTREAM now accepts AAC-LC and H.264 in either order in HLS master playlists, including the audio-first variant order used by the public Mux Big Buck Bunny sample. [Mux sample manifest](https://test-streams.mux.dev/x36xhzz/x36xhzz.m3u8)


## B7 follow-up on 5467e27

The visible exchanges include RTSP SETUP without a stream list, RECORD, and SETUP stream type 96 (realtime audio). The subsequent /audioMode carries the default audio mode. These establish an audio transport. The X-Apple-Session-ID on the pairing requests is consistent with an AirPlay control connection attempting the next step. The filtered trace reaches its detail cap and cannot prove that Safari never issued /play, that the pairing rejection stopped the handoff, or that Safari selected a particular video protocol.

The mask difference is 1 << 42. UxAir sets bit 42 for the experimental HEVC mirroring profile and clears it for H.264. Each receiver start has one mask. Both DNS-SD records derive from it (_airplay._tcp uses features and _raop._tcp uses ft), and both SRV records point to the same TCP listener. Plain /info and /server-info return that mask and qualified /info requests expose the actual TXT records. The two log lines describe separate receiver starts with different HEVC settings. Bits 0 and 4 continue to describe the development build's experimental URL video and HLS path. Bit 27 advertises the legacy pairing modes supported by the pinned receiver. The model and source version identify the legacy compatibility profile. The inherited mask set bit 2 for FairPlay-protected video even though UxAir has no corresponding protected-video transport. The development video profile now clears bit 2. The resulting masks are 000004005a7ffef3 for HEVC mirroring and 000000005a7ffef3 for H.264. /fp-setup2 returns an explicit unsupported response. Legacy RAOP stream-key setup uses /fp-setup and has a separate advertisement. The pinned bitmap also contains photo, slideshow and photo-preload bits, while UxAir exposes no corresponding rendering route. The correction here is scoped to protected video. Modern video queue, unified control, buffered audio and HomeKit pairing bits are clear. [Feature declarations in UxPlay](https://github.com/FDH2/UxPlay/blob/48f5ce47c9ef694afccfac907c9e8828329657fe/uxplay.cpp#L2475) · [Pinned DNS-SD TXT construction](https://github.com/FDH2/UxPlay/blob/9f3c2bbc658645533fa1057e76c29ec8c947fa0f/lib/mdnsd/dnssd_mdnsd.c) · [UxPlay pairing notes](https://github.com/FDH2/UxPlay/wiki/AirPlay2-protocol)

In 5467e27, cseq=0 was a Boolean indicating an absent header, not the header value zero. session_header=1 indicated X-Apple-Session-ID, not RTSP Session. The development dispatcher tested its video endpoint list and then returned 501 from the pinned no-CSeq/HLS gate. The pairing handlers were below that gate, so they had no opportunity to assess the request. A valid CSeq allows RTSP to reach the existing RAOP pairing dispatcher on the same listener. Missing CSeq does not imply bad credentials. Invalid CSeq and zero have separate outcomes. RTSP defines CSeq for its exchanges, but the receiver has observed AirPlay handoff requests using an RTSP request line without that header. [Pinned request dispatcher](https://github.com/FDH2/UxPlay/blob/9f3c2bbc658645533fa1057e76c29ec8c947fa0f/lib/raop.c) · [RTSP 1.0 CSeq](https://www.rfc-editor.org/rfc/rfc2326#section-12.17)

The development dispatcher now recognizes legacy /pair-setup and /pair-verify over HTTP/1.1 and RTSP/1.0 without CSeq when a bounded X-Apple-Session-ID is present. /pair-setup returns the receiver's public key. /pair-verify requires a controller key already registered through the existing PIN flow and verifies a matching proof on the same connection with the pinned pairing primitives. Pairing on this route does not change the RAOP connection type, stop an audio transport, register a key, or authorize a different connection. A standard RTSP Session header alone does not select the video pairing route. Unsupported body shapes get an explicit error instead of being treated as authenticated. The PIN flow and CSeq-based RTSP pairing use the existing handlers. The video routes still require their own session admission and the player must report progress before playback is reported ready.

UxPlay documents an initial RAOP setup followed by a separate video pairing connection, /server-info, a PTTH event connection and /play for its HLS example. The Android issue documents one real Safari HTTPS /play handoff reaching ExoPlayer. PhairPlay implements URL playback routes and legacy PIN, pair-verify and FairPlay stream-key setup. RPiPlay is a mirroring receiver. Shairport Sync implements modern pairing and encrypted control for its AirPlay 2 audio path, which includes realtime and buffered audio. These sources distinguish classic URL handoff, FCUP relaying, mirroring and audio. The B7 excerpts do not identify an HKP/TLV8 exchange, encrypted control, a FairPlay requirement, or a FCUP request. Those mechanisms require their own observed negotiation and transport before expanding support. This change reuses the pinned GPLv3 UxPlay implementation and adds no third-party code. [UxPlay HLS sequence](https://github.com/FDH2/UxPlay/wiki/experimental-version-of-UxPlay-with-support-for-HLS-video-streaming-(you-tube-movies)) · [Android Safari report](https://github.com/jqssun/android-airplay-server/issues/79) · [PhairPlay routing and pairing](https://github.com/JObersi10/PhairPlay/blob/39506518e82e49833f590c7b90007586fa43be9d/app/src/main/kotlin/com/phairplay/airplay/RtspHandler.kt) · [RPiPlay](https://github.com/FD-/RPiPlay) · [Shairport Sync RTSP source](https://github.com/mikebrady/shairport-sync/blob/master/rtsp.c)

The wire trace now identifies the shared listener port and assigns each parsed connection a local number. It logs only allowlisted paths, CSeq format and the presence of both session headers. Keyed aliases let the same opaque header value be matched on different connections during one receiver start. They do not carry authority. Pairing events report route, reason and observed proof state. Polls, pairing, video control and ordinary traffic have separate detail limits. Listener summaries count video controls, accepted audio-only SETUPs, observable pairing failures, unknown or unsupported exchanges, and admitted /play commands, including events after their detail budget is full. Counts describe parsed traffic at this listener. Redacted paths and parser failures still cannot identify an alternate protocol by themselves.


## B7 follow-up on 15e0c54

The latest B7 trace records a valid /pair-verify proof and /server-info followed by HTTP /fp-setup on the verified connection. In this build only /pair-setup and /pair-verify bypass the no-CSeq gate for authentication. The direct HTTP route list contains /fp-setup2 but omits /fp-setup. The only pinned /fp-setup handler is selected later for RTSP. As a result the development dispatcher returns 501 with no-cseq-route before consulting video verification or the FairPlay transport code. This is the first confirmed failure after verification. The supplied extract lacks the full property names and seek targets, and the listener recorded zero admissions. It does not establish whether Safari sent /play or which subsequent rejection also prevented it. The development HTTP path now validates the legacy v3 FPLY transport exchange on the socket that verified the controller. The existing pinned transport functions produce the binary replies for its 16-byte setup and 164-byte follow-up. A replay on a different connection, a conflicting session ID, a malformed frame and an unsupported variant receive explicit errors. This path uses separate state from RAOP and never passes transport material to the video player. /fp-setup2 and protected video are unsupported. The protected-video feature bit stays clear. A legacy transport exchange alone does not establish that the requested media is protected, and UxAir only admits the already supported HTTP(S) media descriptors. [Apple FairPlay Streaming](https://developer.apple.com/streaming/fps/) · [PhairPlay transport dispatcher](https://github.com/JObersi10/PhairPlay/blob/39506518e82e49833f590c7b90007586fa43be9d/app/src/main/kotlin/com/phairplay/airplay/RtspHandler.kt)

The baseline routes PUT /setProperty to DirectSession, where setters with a query explicitly return 501. The older wire logger hides query values and does not inspect the binary plist, so the supplied log cannot identify which property was requested. The new trace records an allowlisted property name and the shape of its value. On a verified connection the receiver accepts the documented invalid-time resets for forwardEndTime and reverseEndTime, advancement when no next item exists, and opting out of date-range notifications. These settings describe the single-item player's actual behavior. It returns a binary-plist result for those assignments and explicit errors for unsupported values or malformed requests. The player has no configurable time boundaries, subtitle selection or interstitial scheduler. [Wire examples for /setProperty and /scrub](https://openairplay.github.io/airplay-spec/video/http_requests.html) · [Media cast trace](https://air-display.github.io/airplay-internal/media_cast_service.html)

The latter fits the zero-admission count, but the excerpt lacks enough detail to distinguish them for the reported request. A malformed position has a separate 400 response. A seek before /play is rejected rather than applied to an unknown item. Sequence numbers beside connection IDs show request order and gaps after the detail cap.
