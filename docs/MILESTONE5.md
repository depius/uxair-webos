# Milestone 5A: 4K HEVC mirroring capability audit

> Historical development record. See [UxAir 1.2.0 scope](UXAIR_1_2_SCOPE.md) for current release and validation status.

Target: LG OLED B7, Rockhopper 3.9.0, ARMv7. This audit stops before enabling HEVC advertisement or changing playback. The owner-verified H.264 1080p/30 mode and 720p/30 fallback remain intact.

## B7 decoder and UHD output evidence

[LG's webOS TV 3.5 format table](https://webostv.developer.lge.com/develop/specifications/video-audio-35) lists HEVC Main and Main10 up to 4096×2160/60 for UHD models, with bitrate/container constraints. That is TV playback support, **not** a published guarantee for this app's raw elementary-stream `BUFFERSTREAM` interface. The working [Starfish/ACB loader](../src/media_starfish.cpp) requests `externalStreamingInfo.contents.codec.video="H264"`, `format="RAW"`, a maximum 2 MiB video source buffer, and a 30 FPS/720p-or-1080p adaptive limit. `Media::open` rejects source-buffer limits above 2 MiB. No verified Rockhopper codec token, load schema, accepted HEVC Annex B parameter-set arrangement, maximum `Feed` size, or failure/timeout behavior is available for HEVC. The present `Load`/`Play` traces demonstrate H.264 only.

The same media code places video through `AcbAPI_setDisplayWindow`, but has not measured an independently reported 3840×2160 video-plane output. [LG's app-resolution table](https://webostv.developer.lge.com/develop/specifications/app-resolution) distinguishes UHD **video playback** from 1920×1080 **graphics** on UHD sets; it is not a measurement of this native app's Starfish plane. An HEVC SPS of 3840×2160 would prove input dimensions, not displayed resolution. A successful `Feed` return is not a presented-frame event; existing `FRAMEREADY` callbacks are too sparse to label as displayed FPS.

The [profile and packet limits](../src/settings.cpp) allow only H.264 720p/1080p at 30 FPS, with 1–2 MiB video packets and 4–8 MiB queues. The [H.264 parser](../src/h264.cpp) validates only H.264 SPS and a 2,073,600-pixel maximum. There is no HEVC SPS/profile/bit-depth validation, UHD queue budget, or distinct 4K H.264 profile. Main10 decode capability in LG's format table cannot be treated as supported SDR output from this app, and HDR metadata/output signaling remains outside this milestone.

## Decision and evidence required to resume

**Stop after Phase 5A.** A technically defensible Starfish/ACB HEVC initialization path has not been established. Enabling bit 42 or a selectable UHD profile now would promise a decoder path that this build has not demonstrated it can initialize or safely validate. No experimental setting, diagnostics label, or IPK claiming HEVC/4K is added.

The smallest safe next investigation is a separate, explicitly invoked **local decoder probe**, without AirPlay advertisement or modifications to firmware/system libraries. It should use the same pinned SDK and app-private data area, exercise a short, licensed or self-generated HEVC Main 8-bit SDR Annex B sample first at 1080p and then at 3840×2160, and log only `Load`/`Play`/`Feed` outcomes, source SPS dimensions, Starfish video-info fields, ACB window dimensions, decoder errors and memory. The Rockhopper HEVC codec token and RAW bufferstream contract must first be obtained from a firmware-specific header, documented API, or a verified native-app trace; do not guess `H265` or `HEVC`. The probe must have bounded input, a timeout, explicit cleanup and no network listener. Read-only inspection of the TV's available API documentation/headers is preferable before generating this probe. Ask the owner to run any hardware probe manually and retain the current development IPK for rollback.

If that probe demonstrates HEVC Main 8-bit decoding and a genuine UHD output plane, then: (1) harden and test the pinned mirror parameter-set path without replacing the core; (2) add a bounded HEVC SPS/profile parser and separated queue limits; (3) add an idle-only, disabled-by-default setting with safe-start H.264 recovery; (4) enable bit 42 only for that proven path; (5) check actual sender codec/SPS, input/feed timing and independent output evidence on the B7. Test 1080p H.264 and 720p fallback before and after. Do not infer Main10, 60 FPS or HDR support from a Main 8-bit SDR result.

No hardware probe, HEVC sender session or UHD plane measurement has been performed in this audit. Native tests and cross-compilation can validate existing behavior and documentation but cannot resolve the Rockhopper decoder contract.

The [5B firmware-discovery procedure](MILESTONE5B.md) records a candidate `H265` token found in an independent SMP client, the conflicting webOS 3.x compatibility evidence and bounded read-only commands for the owner. It still does not establish HEVC operation on this B7.
