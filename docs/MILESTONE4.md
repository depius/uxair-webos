# Milestone 4A/4B: TV controls and direct-media feasibility

## Hardware baseline and UI validation

The owner tested the previous development IPK on an LG OLED B7 running Rockhopper 3.9.0: H.264 mirroring negotiated **actual 1920×1080 SPS at 30 FPS**, with no reported frame drops; Magic Remote AN-MR650 direction/OK and the playback overlay worked. This establishes the prior build, not this new UI package. The 720p/30 profile remains the default and recovery choice. Mirroring, pairing, audio, Starfish and ACB code paths are unchanged in 4A.

The new idle screen has five sidebar sections: Screen Mirroring, Photos & Video, Playback Diagnostics, Usage Statistics and System Settings. Left/Right changes section; Up/Down changes row; OK opens a choice dialog; Up/Down then OK commits; Back cancels. The current persisted choice has a checkmark. A pointer left click can select a section, row or dialog choice. Disabled rows describe the missing capability. Back from a section returns to Screen Mirroring; Back there exits only when idle. During playback OK opens the live diagnostics page, Back hides it, and Back again ends the session. The existing Exit key remains available.

Resolution selection is allowed only while the receiver has no active sender or pairing exchange. The dialog explicitly asks for a sender reconnect. A failed receiver start restores the prior profile; a failed 1080p decoder start restores 720p for the next session. `state/settings-v1`, `state/audio-delay-ms`, usage history and pairing files keep their existing locations and formats. The usage-reset dialog only writes `state/usage-v1` after the destructive choice is confirmed. The System page reads the package's `build-info.txt` to show its exact source commit and version; packaging validates this file and still excludes private state.

**TV procedure for this UI package:** Keep a copy of the previously working `.dev` IPK. Install the new `.dev` IPK manually using the [development package instructions](DEVELOPMENT-IPK.md). With no sender, visit all five sections using direction/OK, open and cancel every selection dialog, change the overlay and HDR policy, reset usage only if desired, and relaunch to check persistence. Check that pairing remains intact. With the sender disconnected, choose 720p, reconnect and test portrait/landscape photos, video and stereo audio. Then disconnect, choose 1080p, reconnect and verify the live **Incoming SPS** reads 1920×1080; check no drops/retries and compare image quality with the previous IPK. During playback, open and close the diagnostics page and confirm video and overlay remain visible. Revert to 720p through the same dialog if needed. This package has not been installed on the TV by CI.

## Pinned protocol implementation

The receiver pins UxPlay 1.74 at `9f3c2bbc658645533fa1057e76c29ec8c947fa0f`. The fork's [receiver callbacks](../src/receiver.cpp) accept H.264 mirroring and audio. They reject H.265 at codec negotiation, drop `is_h265` video, and clear DNS-SD feature bits for direct video, HLS and multi-codec mirroring. [The pinned core's request dispatcher](https://github.com/FDH2/UxPlay/blob/9f3c2bbc658645533fa1057e76c29ec8c947fa0f/lib/raop.c#L242-L245) ignores non-RAOP AirPlay HTTP requests when `hls_support` is false. With HLS enabled upstream, the dispatcher recognizes `/reverse`, `/play`, `/getProperty`, `/setProperty`, `/scrub`, `/rate`, `/stop`, `/action`, `/server-info`, `/playback-info` and HLS fetches; it has **no `/photo` handler**. This is a code finding, not a claim that a current iPhone Photos app necessarily sends `/photo`.

[The pinned `/play` handler](https://github.com/FDH2/UxPlay/blob/9f3c2bbc658645533fa1057e76c29ec8c947fa0f/lib/http_handlers.h#L665-L875) expects a binary plist and `X-Apple-Session-ID`. It can request a `/master.m3u8` playlist via the FCUP reverse channel or pass an HTTP(S) `Content-Location` to `on_video_play`. It has a YouTube process-name allowlist for the playlist case. [Upstream's 1.74 documentation](https://github.com/FDH2/UxPlay/blob/9f3c2bbc658645533fa1057e76c29ec8c947fa0f/README.md) describes HLS as currently supporting YouTube iOS video, not general Photos or full AirPlay 2 direct media. The fork has no `on_video_play` player integration and packages no HLS player. Merely switching on HLS could hand sender-supplied URLs to a player without URL validation, so it is not a safe implementation shortcut.

**Unknown:** No redacted request-method/path trace from the owner's iPhone Photos app has been captured. We cannot yet say whether its photo and video shares use legacy photo upload, `/play` with a URL/playlist, a newer AirPlay 2 transaction, or a mix by iOS version and media type. Before implementation, capture method/path, content type, bounded body size, negotiation response and sender iOS version in an isolated development build, omitting tokens, URLs, pairing material and media bytes from shared logs. Replay representative, malformed and oversized requests in host tests. Do not log raw private photo payloads.

## B7 hardware and application-path evidence

[LG's webOS TV 3.5 format table](https://webostv.developer.lge.com/develop/specifications/video-audio-35) lists HEVC Main/Main10 and H.264 up to 4096×2160 at 60p for Ultra HD models, subject to bitrate/container constraints. [LG's B7 specifications](https://www.lg.com/au/tv-soundbars/oled-tv/oled65b7t/) list a 3840×2160 panel, HEVC USB playback, HDR10, HLG and Dolby Vision. These establish *TV product capabilities*, not that this app's `BUFFERSTREAM` Starfish/ACB API exposes the same codec, 10-bit color or HDR output controls. [LG's streaming specification](https://webostv.developer.lge.com/develop/specifications/streaming-protocol-drm) also says HLS is supported but webOS 3.5 has protocol limitations, including no `EXT-X-MEDIA`; a modern sender playlist may therefore require adaptation or fail.

The fork's [media initialization](../src/media_starfish.cpp) explicitly sets `codec.video=H264`, 30 FPS, RAW bufferstream, and a maximum 2 MiB source buffer. The [H.264 parser](../src/h264.cpp) and [profile limits](../src/settings.cpp) reject dimensions outside the selected 720p or 1080p budget. The [SDL shell](../src/shell.cpp) renders at app resolution and has no still-image decoder or verified 4K/color-managed rendering path. No code extracts HEVC bit depth, VUI transfer/primaries/matrix, mastering metadata or content-light metadata and forwards them to Starfish. The specific Rockhopper 3.9.0 Starfish/ACB API for HEVC, HDR signaling, output color space and still-image planes has **not** been verified on the B7; the existing H.264 Load trace is insufficient evidence. The firmware's GStreamer caps warnings during initialization are unresolved, so codec changes need isolated probing and error handling.

| Goal | Evidence and blocker | Current status |
| --- | --- | --- |
| Direct 4K SDR photograph | No captured Photos request, upload handler, bounded still-image decoder or native-resolution display path. A 4K panel does not imply a 4K SDL app surface. | Feasible to investigate independently; unsupported. |
| Direct 4K SDR video | TV advertises 4K file playback; fork lacks direct-media receiver/player, safe URL policy and 4K Starfish configuration. | Unsupported; firmware API and source protocol need validation. |
| HEVC Main/Main10 | TV format table lists both, but fork rejects H.265 and has no HEVC parser/feed configuration. | Unsupported in this app. |
| HDR10/PQ or HLG video | Panel supports them; no verified sender metadata, bit-depth, BT.2020 colorimetry, mastering metadata propagation or Starfish output-mode control. | Unsupported; Auto remains SDR. |
| HDR photograph | No verified Photos transfer/color profile path or HDR still-image compositor output. | Unsupported independently of HDR video. |
| Dolby Vision | Separate licensed/profile/metadata path; TV product support does not establish AirPlay or app support. | Not planned from current evidence. |

## Recommended next work, after 4B review

1. Use the temporary [Milestone 4C request probe](MILESTONE4C.md) to capture **sanitized** request metadata from actual iPhone Photos photo and video shares, separately from Screen Mirroring, without advertising new features. Determine whether each starts an HTTP photo upload, `/play`, or another route. The probe cannot establish transmitted resolution or codec by itself.
2. Prototype one bounded direct-photo receive/decode/display path only if the trace proves a suitable protocol. Test 4K source pixels and actual display resolution independently, with malformed input limits and no change to mirroring.
3. For direct SDR video, verify a safe sender/local-only URL model, container/HLS variant and Rockhopper Starfish direct-play API before enabling any AirPlay feature bit. Test H.264 first, then separately HEVC Main/Main10 and 4K.
4. Pursue HDR10/PQ and HLG only after a metadata-preserving sender-to-decoder-to-panel trace proves bit depth, transfer, primaries, matrix, mastering metadata and output signaling. Keep Dolby Vision a separate investigation.

The subsequent [4C request probe](MILESTONE4C.md), [4D `/info` experiment](MILESTONE4D.md), and [4E transport/output audit](MILESTONE4E.md) supersede the earlier capture recommendation. Direct photo/video decoding remains disabled.
